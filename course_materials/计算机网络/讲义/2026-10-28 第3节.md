# 计算机网络｜2026-10-28 第3节

本节继续第五章运输层，围绕 TCP 报文段结构、序号与确认号、可变窗口、RTT 与超时重传、选择确认等内容展开。重点是把字节序号、窗口范围和计时器状态联系起来分析，不能只背字段名称。

## TCP 报文段及控制字段（00:45–08:26）

TCP 首部包含源端口、目的端口、序号、确认号、数据偏移、保留位、控制标志、接收窗口、校验和、紧急指针和选项等字段。无选项的基本首部为 20 B；数据偏移以 32 bit 字为单位，表示首部长度而不是整个 TCP 报文段长度。若数据偏移为 5，首部长 $5\times4=20$ B；若存在选项使偏移为 8，则首部长为 32 B。TCP 报文段总长还要加上 TCP 数据长度。

源端口和目的端口标识发送、接收端的应用端点。序号字段以字节为单位描述本方向字节流的位置。确认号字段通常指出接收方期望从对端收到的下一个字节，因而采用累计确认语义。标志位用于建立、拆除连接及数据控制；窗口字段通告接收方当前可以接收多少字节。校验和检测 TCP 首部与数据，并使用 IP 地址和协议等信息构成的伪首部参与校验。

**【理解重点】序号不是报文段编号，而是该报文段首个数据字节的编号。**（03:20–05:42）若首个数据字节序号为 1000，数据长度为 500 B，则下一个字节序号为 1500。若报文段不携带数据，SYN 和 FIN 仍各消耗一个序号空间，因此不能在连接控制题中把序号变化只按数据字节数计算。

### 序号和确认号计算

设发送方当前序号为 $S$，本报文段含 $L$ 个数据字节。若不含 SYN 或 FIN，则下一个序号为 $S+L$，模 $2^{32}$ 运算。接收方连续收到序号从 $S$ 到 $S+L-1$ 的所有字节后，确认号为 $S+L$。确认号说明“下一个希望收到什么”，而不是简单地重复最后收到的字节。

例如服务器收到序号 2000、长度 300 B 的连续数据后，下一期望字节是 2300，因此确认号为 2300。如果后续从 2300 开始的 200 B 到达，确认号前进到 2500。若中间有缺口，累计确认通常停留在缺口起点；后续到达的数据可能被暂存，但确认号不能表示缺失字节已经收到。

TCP 首部最大长度为 60 B，因为数据偏移字段可表示的单位为 32 bit 字，字段最大值 15。可选字段通常包括最大报文段长度 MSS、窗口扩大、时间戳和 SACK 许可等；选项末尾要用填充使首部按 32 bit 对齐。MSS 表示一个 TCP 报文段可承载的最大 TCP 数据量，不包含 IP 和 TCP 首部。若路径 MTU 为 $M$，在 IPv4 无选项且无隧道的简化情况下，MSS 通常不超过 $M-20-20$；实际还要考虑 IP 选项、隧道封装和路径变化。

## 字节流窗口与发送状态（08:26–19:22）

TCP 流量控制使用接收方通告的可变窗口。窗口以字节表示，接收方依据缓存空间决定可通告的容量。发送方在窗口允许范围内发送，避免把接收方的有限缓存压满。发送窗口的左侧对应最早尚未确认的字节；右侧边界由累计确认位置和接收窗口共同确定。确认到来会使左边界前移，窗口广告变化会调整右边界。

分析窗口图时，应把序号线上的字节划分为四类：已确认且已交付的字节；已经发送但尚未确认的字节；允许发送但尚未发送的字节；窗口外、当前不允许发送的字节。接收窗口 $rwnd$ 是接收方通告的缓存余量。发送方实际发送还会受拥塞窗口 $cwnd$ 限制，实际可用窗口通常为 $\min(rwnd,cwnd)$，还要减去已经在途的数据量。

课堂使用 A 向 B 发送多个等长字节区间，展示确认推进和窗口变化（08:34–15:43）。设 B 通告窗口 400 B，A 从序号 1 起发送 1–100、101–200、201–300。若前两个区间收到而第三个缺失，B 的累计确认号为 201。它可以再通告当前接收窗口，A 的窗口左边界移至 201，但缺失区间仍占据在途状态。后续数据即使已发出，也不能据此认为缺失的 201–300 已经确认。

如果 A 收到确认 501，说明此前连续的字节已经被接收至 500，下一期望为 501。若窗口此时为 100，A 当前最多允许覆盖 501–600 这一段。窗口大小改变与确认号变化可能同时发生，解题时应分别记录两者，不能把“窗口为 100”误读为“确认号为 100”。

接收窗口可能降为零，表示接收缓存暂时没有可用空间（15:43–19:22）。发送方停止正常数据发送并等待窗口更新。若窗口恢复通知丢失，双方可能因发送方等待、接收方不再主动发送窗口更新而长期无法恢复。TCP 使用持续计时器定期探测零窗口状态；探测报文段携带少量数据，接收方确认时报告当前窗口。若仍为零，发送方稍后再次探测；若变为非零，则可以恢复传输。零窗口表示流量控制暂停，与网络拥塞导致的拥塞窗口收缩属于不同原因。

## RTT 估计与重传定时器（19:22–33:40）

TCP 的重传定时器需要依据往返时间设置。固定超时时间不适合所有路径：RTT 会因排队、路由和拥塞而变化。若定时器小于正常波动，发送方会重复发送仍在途的数据；若过大，丢失恢复将被延迟。TCP 通过测量样本往返时间并平滑估计来更新超时值。

一次测得的样本记为 $SampleRTT$，平滑 RTT 估计可写为：

$$EstimatedRTT=(1-\alpha)EstimatedRTT+\alpha SampleRTT,$$

其中 $0<\alpha<1$，常见讲解取较小权重，使估计不因单次样本剧烈摆动。RTT 偏差估计可写为：

$$DevRTT=(1-\beta)DevRTT+\beta |SampleRTT-EstimatedRTT|.$$

超时值需要留出对偏差的容忍度，典型表达式为：

$$TimeoutInterval=EstimatedRTT+4DevRTT.$$

这些式子是对运行机制的说明。更新顺序应使用更新前的估计值计算偏差样本；实现细节依协议版本可能有所差异。测量 SampleRTT 时，若某一段数据重传后收到确认，确认究竟对应原发送还是重传版本并不明确，故通常不直接用这类样本更新 RTT，这就是 Karn 算法的动机。

当发生超时仍未收到确认，发送方重传最早尚未确认的数据，并通常增大后续超时等待间隔，避免在拥塞时过快重传。重传定时器需要与确认状态配合：累计确认推进后，最早未确认字节改变，定时器所代表的等待对象也随之改变。若已有多段数据同时在途，一次超时通常针对最早未确认数据，而不是无条件重传所有数据。

## 选择确认与多个缺口（33:40–44:45）

累计确认可以高效表达连续收到的字节前缀，但在中间缺失时不能指出接收方已经缓存的所有后续数据。假设字节区间 1–100 和 201–300 已到达，101–200 缺失；累计确认停留在 101，单看该确认无法知道后面的区间已经缓存。发送方若只依赖累计确认，可能需要重传更大范围的数据。

SACK（Selective Acknowledgment）选项允许接收方在累计确认之外报告已收到的非连续区块。它不会改变累计确认号的基本含义，仍以最早缺失的连续字节为确认位置；SACK 块则帮助发送方识别已经成功到达的后续区间，避免不必要地重传这些区间。SACK 许可需要在连接建立时协商，发送方与接收方都要支持相应机制。

构造窗口与 SACK 题时，建议画出序号轴并标出已确认前缀、缺失区段、已缓存区段和窗口右边界。逐项回答：累计确认号是多少；接收方报告了哪些 SACK 块；发送方当前允许发送到哪里；超时或快速重传机制触发时哪些字节需要重传。SACK 块的报告并不等同于应用已经按序收到了所有数据，TCP 仍需按序向应用交付字节流。

## TCP 可靠传输中的易混概念（44:45–51:17）

窗口大小、序号空间与数据长度各自使用不同含义。序号空间是 32 bit 循环计数器；窗口是当前可发送或接收的字节范围；MSS 限定单段负载长度。若序号接近 $2^{32}-1$，字节序号会回绕到 0，比较时需使用模运算语义，不能用普通整数大小关系处理所有情况。

收到重复确认可能表示后续数据已经到达但前方存在缺口，也可能是重复报文或网络行为所致。快速重传利用连续重复确认尽早重传缺失段，无需等待完整超时。具体触发阈值和算法依实现及协议规定；本节的关键是理解重复确认提供了“接收方仍等待同一个字节”的反馈。

**【理解重点】TCP 的可靠性是端点之间的协议结果。**网络层仍可能丢弃或重排数据，TCP 依靠端点维护序号、确认、缓存、计时器和重传恢复有序字节流。应用读取到字节不代表一次写入对应一条消息；收到确认也只表示远端 TCP 已接收相应字节范围，不等于远端应用已经完成业务处理。

## 公式与窗口题的完整演算方法（08:26–19:22；33:40–47:41）

TCP 序号题、窗口题和重传题常常放在同一个时序图中，作答前先确定题目每一步的已知状态。可以按下面的记录顺序推进：

1. 写明当前方向的最早未确认字节序号 $S_{una}$。
2. 写明下一个新字节序号 $S_{next}$。
3. 写明接收方累计确认号 $ACK$，其含义为对端下一步期望的字节。
4. 写明接收方通告窗口 $rwnd$、发送方拥塞窗口 $cwnd$ 和窗口右边界。
5. 列出已经发送的数据区间与尚未确认的数据区间。
6. 根据收到的确认、窗口通告、重复确认或超时事件更新状态。

若当前累计确认号为 1001，接收窗口为 500 B，则接收方当前允许的后续序号范围从 1001 开始，直到右边界 1501 前的最后一个字节；实现窗口的边界表示时应核对题目采用的左闭右开还是首尾均包含习惯。若已发送区间 1001–1200 且尚未确认，接下来可发送的数据只能从 1201 起，并受剩余窗口与拥塞窗口共同约束。计算剩余可发字节数时，不要把已发未确认的 200 B 再算一遍。

### 字节序号的边界与回绕

32 bit 序号字段可以表示 $2^{32}$ 个不同值，随后从 0 继续编号。窗口比较要依据模序号空间的规则。课堂示例多使用较小序号，方便跟踪；遇到接近回绕的序号时，应先转换成相对于当前窗口左边界的距离，再判断顺序。若窗口长度和序号空间条件不满足安全比较要求，单纯比较无符号整数的大小会得到错误顺序。

确认号累积确认连续前缀。收到缺口之前的数据，不影响确认号前进；缺口之后的数据若被接收端缓存，也不会让累计确认越过缺口。SACK 报告这些后续区间，是为了让发送方能区分“还没到达”与“已经到达但未按序”的数据。接收方仍按序交付给应用，缓存一个区间不代表应用立即可读到该区间。

## RTT、偏差与 RTO 的计算例子（19:22–44:01）

TCP 连接是在运输层维护状态，而底层 IP 转发并不保证每个分组走相同路径。某些分组可能遇到队列拥塞，另一些走不同路径，因此 RTT 样本的波动可相当明显（33:47–35:42）。固定定时器若依据一次偶然偏短的样本设置，可能过早重传；若按特别长的值等待，则真实丢失的发现滞后。

设旧的平滑往返时间为 $SRTT_{old}$，新测量样本为 $R$，平滑系数为 $\alpha$：

$$SRTT_{new}=(1-\alpha)SRTT_{old}+\alpha R.$$

课堂给出的建议值为 $\alpha=1/8$（36:18–37:50）。较小的 $\alpha$ 使历史估计保留较大权重，新样本对结果的改变较缓；较大的 $\alpha$ 更快跟随近期网络变化，也更容易受单次尖峰影响。

还需估计偏差。以 $D$ 代表旧的 RTT 偏差估计，常用平滑形式是：

$$RTTDev_{new}=(1-\beta)RTTDev_{old}+\beta |R-SRTT|.$$

课堂建议 $\beta=1/4$（38:12–39:45）。超时重传时间设为：

$$RTO=SRTT+4RTTDev.$$

偏差越大，$RTO$ 留出的安全余量越多。计算题必须按题目指定的样本顺序和旧值更新；不能把最新样本直接当作 $SRTT$，也不能把 $4RTTDev$ 漏掉。

举例：假设旧 $SRTT=200$ ms，新样本 $R=280$ ms，$\alpha=1/8$，则新估计为 $200\times7/8+280\times1/8=210$ ms。若旧偏差为 20 ms，按新偏差计算时相对平滑 RTT 的差为 $|280-210|=70$ ms，因此新偏差为 $20\times3/4+70\times1/4=32.5$ ms，新的 RTO 为 $210+4\times32.5=340$ ms。示例用于演示公式；真实 TCP 更新中需严格按规范确定在计算偏差时使用的更新前后估计值。

若一个报文段发生重传后收到确认，发送方不容易知道该确认对应原始报文段还是重传报文段（40:49–42:24）。两者发送时间不同，测得的 RTT 会产生歧义。课堂采用的处理规则是不将重传数据对应的确认作为 RTT 采样。这样减少错误样本，但当网络突然变慢时，连续重传的样本缺失可能使平滑估计更新不及时，因此超时后通常采用指数退避逐次延长等待间隔（42:24–43:58）。

### 三种计时行为的区分

| 事件 | 发送端观察 | 主要处理 |
| --- | --- | --- |
| 数据和确认正常到达 | 有可用往返时间样本 | 更新平滑 RTT 与偏差估计 |
| 重传后确认到达 | 原发送和重传的对应关系不确定 | 不把该确认直接作为 RTT 样本 |
| 超时再次发生 | 当前 RTO 内无有效确认 | 重传未确认数据并延长后续等待间隔 |

定时器用于判断是否需要恢复数据，RTT 估计用于选择等待时间；两者相关，但职责不同。不能把“确认号没有前进”与“定时器必然到期”混为同一事件，重复确认可能在超时前就提供缺口线索。

## SACK 选项编码与边界推理（44:01–47:41）

接收方可以缓存乱序到达的字节区块，并通过选择确认列出区块边界。每个区块需要左右两个 32 bit 边界，所以每个 SACK 块占 8 B。TCP 选项空间最多 40 B，但其中还要放置选项类型、长度等字段；因此报文段能够携带的区块数有限。教师指出，SACK 支持需在连接建立阶段由双方通过选项协商；默认协商情况和本课演示设定要以题目为准（45:04–47:30）。

SACK 不取代 TCP 头部的累计确认号。若累计确认号为 $x$，接收方报告区块 $[y,z)$，含义是它已收到从 $y$ 开始到 $z$ 前一个字节的内容，但仍在等待从 $x$ 开始的连续字节。区间采用的首尾表达应依据协议说明；作答时可明确写成半开区间避免边界重复。

示例：接收方已连续收到 1000–1199，缺少 1200–1299，却收到 1300–1499。累计确认号是 1200；SACK 可报告已收到的后续区块 1300–1500（半开区间）。发送方据此知道 1300–1499 不需要重传，优先恢复缺失的 1200–1299。若之后又收到 1500–1599，接收端可以扩展已缓存区间；确认号仍不能越过 1200，直到缺口补齐。

**【理解重点】SACK 描述的是接收端缓存中已到达的非连续范围。**（44:01–47:41）它为发送方提供更精确的重传信息，但没有让 TCP 改为无序交付。题目若给出多处缺失，应先根据累计确认找到首个缺口，再看 SACK 块覆盖哪些后续字节，最后列出真正未收到的数据。

## 课堂判断题回顾（48:48–51:06）

教师用课堂答题核对 TCP 与 UDP 的边界（49:44–50:16）：UDP 保留应用提交的数据报边界，TCP 按字节流服务，TCP 报文段长度由 TCP 的发送与分段机制决定。应用交给 TCP 的写入长度不能直接推出 TCP 报文段长度；MSS、窗口、缓存、拥塞状态和发送策略都会影响分段。

流量控制则通过窗口通告调节发送方进入接收缓存的数据量，目标是使接收方有能力接收（50:32–51:06）。教师特别指出滑动窗口机制与窗口通告相关。网络拥塞控制另有 $cwnd$ 等状态，二者最终共同限制发送量，但流量控制关注接收端能力，拥塞控制关注路径中的共享网络资源。

## 考试计算时的核对清单（03:20–05:42；08:26–19:22；33:40–47:41）

遇到一题同时涉及序号和确认号时，先确认数字单位是不是字节，再确认该报文段是否带有 SYN 或 FIN。计算数据范围时，将起始序号与数据长度结合；计算下一个序号时，使用首字节序号加数据字节数，再处理标志位消耗的序号。确认号写成接收方下一步期望的字节，不写成最后一个收到字节的序号。

遇到可变窗口图，需分清接收窗口通告与发送方当前窗口。接收方通告的是缓存可用容量；发送方受累计确认位置、接收窗口、拥塞窗口及已经发送但尚未确认的数据共同约束。窗口通告发生变化时，即使没有收到新数据确认，窗口右边界也可能变化；确认推进时，即使窗口大小相同，整个窗口范围也会向前移动。

遇到 RTT 更新题，把每一次样本时间列成表格，逐行更新 $SRTT$、偏差与 $RTO$。注意权重分别作用于旧估计和新样本，且权重之和为 1。若题目提供的是重传报文段的确认，按课堂说明排除其样本；若题目给出连续超时，则更新等待间隔，不要继续使用同一固定数值。

遇到 SACK 题，把每个区块的两个边界写全，注明边界解释方式。累计确认号仍是最早缺失的连续字节，SACK 区块是其后的已接收数据。用图或区间集合查明缺失部分，比直接看一个最大序号可靠。收到更早缺失区块后，若后续区块已经缓存，累计确认可以一次向前跨过多个连续区段；其变化量可能大于本次重传段长度。

上述方法也可用于检查答案的一致性：确认号不应大于第一个尚未收到的字节；SACK 区块不应包含接收端尚未收到的数据；发送方的新数据不能越过当前有效窗口；超时重传不改变数据字节本身的序号；同一段数据重传不会因此产生新的应用字节。计算完成后逐条对照这些关系，能发现常见的区间端点错误。

## TCP 字节流与应用读取的联系（00:45–03:20；49:44–50:16）

教师在课前复习和课堂判断题中再次区分 TCP 与 UDP：UDP 的数据报保留一次发送所形成的边界，TCP 则把应用写入内容作为连续字节流处理。TCP 的报文段长度由 TCP 的分段和发送状态决定，而非由应用一次写入的长度决定。应用协议若需要消息边界，应在字节流中加入长度字段、固定长度或分隔符，并在接收端实现完整读取逻辑。

这个差别会影响窗口题中的“数据段”一词。课堂图表可能把字节区间称为一个报文段，便于列出发送顺序；真实 TCP 可以把应用数据拆成多个报文段，也可能将多个较小写入合并。计算题给出 MSS、报文段负载或发送区间时，以题设数据为准；如果题目只给出应用调用次数，不能据此推断 TCP 报文段个数。

## 接收缓存与确认进度之间的联系（08:26–19:22；49:44–51:06）

接收方收到连续字节后可以提升累计确认号；确认号提升反映接收端按序接收的进度。接收窗口则描述接收缓存的可用空间，两者虽然常在同一 ACK 报文中一起出现，语义并不相同。窗口为零时，ACK 仍可以确认此前收到的数据；窗口为正时，ACK 也可能因为某个缺口而停留在较早序号。

例如，接收方连续收到 1–1000，之后收到 1201–1300，但 1001–1200 缺失。若接收缓存还有空间，接收方可能通告正窗口并通过 SACK 报告 1201–1300；累计确认仍为 1001。题目若只给窗口字段，不足以判定所有数据是否按序到达；还需结合确认号和可能出现的 SACK 区块。

## 本节各机制的因果顺序（01:12–51:06）

可变接收窗口先限制发送方能向一个接收端推送的数据量；MSS 与发送时机决定缓存中的字节何时被封装成 TCP 报文段；序号与确认号记录字节流接收进度；RTT 估计和超时计时器发现长时间未获确认的区段；SACK 补充说明缺口之后哪些数据已到达；拥塞窗口从网络路径角度再限制进入共享网络的数据。它们共同约束 TCP，但每个字段或变量都回答不同的问题。

复习时可以用一个问题检验理解：接收窗口很大、拥塞窗口很小，发送方会受哪个限制？答案是拥塞窗口；累计确认停在缺口但 SACK 显示后续区段已到达，发送方需要重传哪些数据？优先恢复缺失区段；收到零窗口但定时器尚未到期，能否继续发送常规数据？不能越过接收端的通告窗口；一个字节序号被重传后，是否创建新的字节流位置？不会，重传的是同一序号范围。
