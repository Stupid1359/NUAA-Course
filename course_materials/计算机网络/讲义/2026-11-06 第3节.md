# 计算机网络｜2026-11-06 第3节

本节接续 DNS，讲解迭代与递归查询、域名缓存和可靠性；随后回顾 Web 文档、HTTP/1.0 与 HTTP/1.1 的连接行为、代理缓存、动态与活动文档；后半段介绍电子邮件系统、SMTP、POP3 和 IMAP。课堂将应用层作为相对较少的考核内容，讲授重点在概念关系和协议用途，具体范围以第40节复习说明为准。

## DNS 服务器层级与分布式查询（01:20–05:26）

DNS 把层次化域名映射为 IP 地址。查询涉及根域名服务器、顶级域名服务器、权威域名服务器和本地域名服务器。层级划分使名称空间能够由不同管理单位分别维护：根服务器提供顶级域的引导信息；顶级域服务器维护该域下委派出去的二级域信息；权威服务器负责一个或多个具体区域中的记录；本地域名服务器为接入网络中的主机处理查询并缓存结果。

例如，用户查询 `www.example.com` 时，本地域名服务器可以先询问根服务器。根服务器通常不会直接给出主机的最终 IP 地址，而会返回 `.com` 顶级域服务器的地址。本地服务器再向顶级域服务器查询，顶级域服务器给出 `example.com` 区域的权威服务器信息。本地服务器继续查询权威服务器，取得所需记录后将结果返回给用户。若被查询的权威服务器只知道下一层服务器，也会给出下一步线索，整个解析可能经过多轮交互（02:14–04:39）。

13 个根服务器名称代表逻辑上的根服务器集合，实际服务由分布在各地的镜像节点提供。课堂解释其设置与系统规模、负载分布有关（01:35–02:08）。理解 DNS 时应将“逻辑名称”和“物理部署节点”区分开；查询逻辑仍沿域名层级转交，实际请求可由多个地理位置的节点承担。

### 递归和迭代查询

“递归”与“迭代”描述查询责任由谁继续承担，不是两类不同的域名记录。主机把完整问题交给本地 DNS，并等待它返回最终结果，这一段对主机而言是递归查询；本地域名服务器继续访问根、顶级域和权威服务器，逐步取得下一步服务器地址并自行查询，属于迭代过程（07:09–10:08）。

| 阶段 | 查询发起者 | 被询问者的典型响应 | 谁继续找下一台服务器 |
| --- | --- | --- | --- |
| 主机查询本地 DNS | 主机 | 最终答案或错误信息 | 本地 DNS |
| 本地 DNS 查询根服务器 | 本地 DNS | 顶级域服务器线索 | 本地 DNS |
| 本地 DNS 查询顶级域服务器 | 本地 DNS | 权威服务器线索 | 本地 DNS |
| 本地 DNS 查询权威服务器 | 本地 DNS | 最终资源记录或更细线索 | 本地 DNS 或按响应继续 |

递归查询也可从逻辑上继续委托其他服务器完成，但根层承担全球大量客户查询会带来极高负载。课堂指出互联网中更常见的模式是主机到本地 DNS 使用递归，本地 DNS 到层级服务器使用迭代（08:03–10:57）。答题应指出每段查询的发起方和响应内容，不能笼统说“DNS 全程都是递归”或“全程都是迭代”。

**【理解重点】迭代响应常给出下一步查询线索，不一定直接给出最终 IP。**（02:27–04:39）若收到的是委派或服务器地址，本地域名服务器还需按该线索继续查询。用户最终看到的结果可能来自多次服务器交互。

## DNS 缓存、刷新与服务可靠性（10:57–12:05）

域名服务器和主机通常都会保存近期查询的名称与地址对应关系。缓存命中时，本地域名服务器可直接返回结果，无需每次都从根开始查询；缓存降低查询延迟，也减少不同 DNS 服务器之间的重复流量（11:00–11:47）。缓存并非永久有效。资源记录包含有效期限，过期后需重新查询，以免长期使用已经变化的映射（11:49–12:05）。

缓存也意味着 DNS 记录更新不会在所有用户处瞬间可见。若权威记录刚有变化，但递归服务器仍持有尚未过期的旧记录，用户可能暂时取得旧地址。定位这类现象时，需要检查记录的有效期限、递归缓存状态和用户所配置的本地 DNS，而不能只看权威区文件。

DNS 是许多 Internet 应用的入口服务。用户记忆域名而非 IP，浏览器访问网站前通常需要完成名称解析；域名服务不可用会令用户难以访问服务，即使网站服务器本身仍然正常（05:29–06:40）。教师据此指出 DNS 会成为拒绝服务攻击目标，并说明主、辅 DNS 服务器可提供冗余，降低单点故障导致的查询中断风险（06:40–07:09）。

冗余部署解决的是可用性问题，缓存解决的是重复查询成本，两者作用不同：缓存减少对远端服务器的依赖；多台 DNS 服务器在某一台不可用时提供备份能力。安全性还需要访问控制、流量过滤和部署策略等共同支持，本节着重讲授基础可靠性思路。

## Web、URL 与 HTTP 所处层次（12:08–14:58）

万维网是分布式超文本服务。文档可包含指向其他文档的链接；超媒体还可包含图片、声音、动画和视频。浏览器充当 Web 客户端，Web 服务器按请求提供文档。浏览器通过 URL 标识要访问的资源，HTTP 负责在客户端与服务器之间交换请求和响应（12:34–13:49）。

静态 HTML 文件由预先准备的内容构成，服务器读取后即可响应。HTML 标记描述文档结构和显示元素；浏览器根据标签解释页面。XML 侧重表达和传输结构化数据，可以与 HTML 配合使用，不能简单理解为 HTML 的替代。CSS 用于描述页面样式和布局，改变外观规则而不直接承担 HTTP 传输功能（21:18–24:18）。

HTTP 是面向事务的应用层协议，常见 Web 请求和响应经 TCP 连接传送。典型过程包括建立 TCP 连接、发送 HTTP 请求、接收响应，再根据版本及连接策略决定是否保留连接。课堂列出早期 HTTP 常用 TCP 80 端口，并提到安全 Web 服务会使用其他端口；具体端口以服务器配置和题目为准（13:49–14:58）。DNS 查询与 HTTP 内容传送属于不同事务，DNS 在本课总结中按 UDP 传送，HTTP 按 TCP 传送。

## HTTP/1.0、HTTP/1.1 与往返时延（15:00–20:04）

早期 HTTP/1.0 的常见工作方式是每个对象请求完成后关闭 TCP 连接。若页面包含 HTML 主文件、图片和其他对象，每取得一个对象都可能再次经历 TCP 建连过程。页面对象多时，重复握手会增加延迟和网络开销（15:08–17:23）。

设一次往返时延为 $RTT$，忽略传输时间时，建立一条 TCP 连接约需一个 RTT；随后发送请求并收到首字节响应又需约一个 RTT。因此一个小对象至少消耗约 $2RTT$，再加上传输对象本身所需时间：

$$T_{object}\approx 2RTT+T_{transmit}$$

若使用非持续连接连续请求多个对象，每个对象可能重复承担建连和请求响应等待。页面含 $n$ 个对象且连接逐个建立时，粗略可写为 $T\approx n(2RTT+T_{transmit})$；此估计忽略服务器处理、并行连接、缓存和对象大小差异，只用于说明建连开销的累积。

HTTP/1.1 引入持续连接，服务器完成一个响应后，在一段时间内保留 TCP 连接供后续请求复用。这样可减少 TCP 建立和释放次数，适合浏览器继续请求同一服务器上的页面对象（17:23–18:22）。持续连接并不等于 HTTP 有状态：协议仍以一次请求和一次响应为基本事务，客户端或服务器若要关联多次事务，需要使用 Cookie、会话标识等机制。

持续连接可以按请求顺序采用非流水线方式，也可在先前响应尚未返回时继续发送后续请求。非流水线方式每完成一个对象再请求下一个，仍需等待多个响应；流水线允许连续发出请求，减少请求之间的空闲等待（18:30–20:04）。课堂以多个页面对象说明流水线可缩短串行请求延迟。题目若要求计算时延，应读清并发连接数量、对象是否同一服务器以及请求是否流水化，不能把所有页面都机械地代入单一公式。

HTTP 代理可在内部缓存常用内容。多个用户请求同一对象时，代理可能直接返回缓存副本，减少访问远端服务器的流量和时延。内容分发网络（CDN）也通过将内容放置在靠近用户的位置改善访问体验。代理缓存适合重复访问内容；个性化或频繁更新内容还要核验新鲜度和缓存规则（20:05–20:56）。

## 静态文档、动态文档与活动文档（21:08–31:39）

三种文档的关键差别在于内容由谁、何时生成，以及代码在哪里执行。

| 文档类型 | 生成位置 | 主要传送内容 | 运行或解释位置 |
| --- | --- | --- | --- |
| 静态文档 | 预先制作并存放于服务器 | 已准备好的文档数据 | 浏览器解释标记并显示 |
| 动态文档 | 服务器收到请求后调用程序生成 | 按请求生成的结果数据 | 服务器执行处理程序，浏览器显示结果 |
| 活动文档 | 服务器提供程序或代码 | 可执行代码及相关数据 | 浏览器端执行并与用户交互 |

动态文档可以根据请求参数查询数据库，再生成 HTML。例如用户提交学期和课程条件，服务器端程序检索相应数据并组合页面。浏览器看到的仍是 HTTP 响应，但服务器端多了应用程序、数据存储和动态文档处理流程（24:21–27:40）。课堂以 CGI（Common Gateway Interface，通用网关接口）说明一种服务器程序被调用并返回动态内容的机制；CGI 是接口方式，具体程序可用不同技术实现（27:41–28:44）。

活动文档则由服务器把代码交给浏览器，在用户设备上运行。客户端运行后可持续更新显示并响应操作（29:04–30:15）。这与动态文档的主要区别是代码执行位置：动态文档的应用程序在服务器端运行，活动文档的代码在客户端运行。客户端执行未知代码可能带来安全风险，用户需要确认来源和权限（30:22–31:39）。

## 电子邮件系统组成与消息流向（32:04–42:31）

电子邮件系统包括用户代理、邮件服务器以及发送和读取邮件的协议。用户代理提供撰写、发送、浏览和管理邮件的界面，可以是桌面客户端，也可以是浏览器中的 Web 邮箱。邮件服务器接收并保存用户邮件，并与其他域的邮件服务器交换消息（32:21–35:45）。

发送邮件时，用户代理把邮件交给自己的邮件服务器；发送方邮件服务器再与收件方邮件服务器建立 SMTP 通信并投递邮件；收件方邮件服务器把邮件保存到邮箱。收件人上线后，通过 POP3 或 IMAP 读取邮件。邮件传递可分成“用户代理到发件服务器”“发件服务器到收件服务器”“收件代理到收件服务器”三个 TCP 会话，各段连接端点不同（40:31–41:09）。

邮件服务器在不同通信方向可承担不同角色。用户代理向本地 SMTP 服务提交邮件时，邮件服务器是服务端；它向远端服务器投递时，发起 SMTP 连接的一方又是客户端。远端服务器接收时作为 SMTP 服务端。角色是相对于当前连接定义的，不是某台服务器永久固定为客户端或服务器（35:51–37:41）。

SMTP 采用推送方式将邮件从发件方逐段送至收件方邮件服务器。接收者不一定一直在线，SMTP 不要求最终用户设备立即取信；邮件抵达收件服务器后可暂存在邮箱。用户代理之后主动发起读取请求，这需要独立的邮件读取协议（37:46–40:08）。

课堂还区分 Web 邮箱和服务器间传送：用户通过浏览器访问自己的邮箱时，浏览器与邮箱网站之间使用 HTTP；两个邮件服务器互相投递时仍可使用 SMTP；收件人用浏览器读取时又是 HTTP（00:44–02:00，第40节开头回顾）。因此不能因用户界面是网页，就认为整个邮件路径都使用 HTTP。

## SMTP 过程、文本格式与抄送字段（42:32–46:51）

SMTP 建立在 TCP 之上，课堂以 TCP 25 端口作为常见服务器端口示例（43:25–44:06）。连接建立后，双方交换命令和响应；响应码表示服务器当前处理状态。课堂例子中 `250` 表示操作成功类响应，`354` 表示服务器已准备接收邮件数据。应用层传输完成后结束 SMTP 会话，再释放 TCP 连接（44:07–45:35）。

电子邮件结构可分为信封信息与内容。信封用于投递和路由；邮件内容含首部与主体。首部包含 `From`、`To`、`Date`、`Subject` 等字段，首部结束后空行分隔主体。SMTP 通过特定结束标记识别邮件数据结束；按协议编码发送数据时，应对正文中可能出现的结束序列作相应处理。课堂重点在识别 SMTP 会话阶段和邮件格式组成，不要求记忆所有命令（44:30–45:58）。

`Cc` 表示抄送，收件人通常可看到抄送名单；`Bcc` 表示密送，其他收件人不会从常规收件字段看到该地址。两者都是向额外接收人发送副本，差别在地址可见性（46:00–46:45）。

## POP3 与 IMAP 的读取方式（46:51–50:34）

POP3 和 IMAP 都用于用户代理读取邮件，但管理方式不同。POP3 通常将邮件下载到客户端；若配置为下载后从服务器删除，客户端本地误删可能令服务器副本也不再保留。邮件按服务器和客户端策略下载，离线时可以读取已经下载到本地的内容（47:06–48:20）。具体是否删除取决于客户端设置，不能把某种默认配置当成协议必然行为。

IMAP 侧重让客户端管理服务器上的邮箱，并支持同步文件夹、查看邮件列表、按需获取正文或附件等操作。用户可以先查看首部或选择下载部分内容，邮件仍可保留在服务器供其他设备读取（48:49–50:02）。IMAP 的在线邮箱管理较灵活；离线读取则取决于客户端是否预先同步相关内容。

| 比较点 | POP3 | IMAP |
| --- | --- | --- |
| 主要使用方式 | 下载邮件到客户端 | 与服务器邮箱保持管理和同步 |
| 服务器副本 | 依客户端策略决定是否保留 | 通常保留并由客户端管理 |
| 部分获取 | 能力较有限 | 可按需查看部分内容或附件 |
| 多设备使用 | 需关注下载与删除设置 | 更适合在多个客户端间同步状态 |
| 离线访问 | 已下载内容可离线查看 | 需事先缓存或同步内容 |

**【理解重点】SMTP 负责投递，POP3/IMAP 负责读取。**（37:46–40:08；46:51–50:34）将两类协议分开，可以解释邮件何以先到服务器邮箱，再由用户主动取回。邮件系统不是一条由发件设备直接连到收件设备的长连接。

### 邮件投递与邮件读取是两段不同工作

发送邮件时，用户代理把消息交给发件方邮件服务器；服务器再依据收件地址的域名找到接收方邮件服务器，并把消息投递到对方邮箱。收件人之后连接自己的邮箱服务器读取消息。SMTP 面向邮件发送和服务器间传递，POP3 与 IMAP 面向用户从邮箱读取邮件。因而只安装一个能收邮件的客户端，并不表示它承担了 Internet 上所有服务器间的投递工作。

课堂用 push 和 pull 说明这一差异：SMTP 一侧通常由发送端主动把邮件推送给下一服务器；POP3 或 IMAP 一侧由收件用户登录后从服务器取回已有邮件。若邮件未到达收件箱，排查时应分辨故障发生在发件客户端提交、服务器间转送、收件服务器接收，还是用户客户端读取阶段。

邮件系统涉及多个服务器和协议，但用户看到的“发件人”“收件人”字段并不完整等同于网络传输路径。传输时使用的信封地址决定服务器把消息交给哪些邮箱；消息正文中的 `From`、`To` 等头字段用于呈现邮件内容。课堂所说的 SMTP 先交互信封，再传输头部与主体，体现了传输路由信息和可见邮件内容的区分（44:21–45:58）。

### SMTP 会话的阅读方法

阅读 SMTP 会话时，可按连接建立、服务器问候、客户端提交发件人和收件人、声明开始数据、发送消息内容、结束数据、退出会话的顺序追踪。课堂给出的连接使用 TCP 25 端口；客户端先建立 TCP 连接，然后按 SMTP 命令与服务器应答交互（43:34–44:12）。命令和响应是文本形式，因此早期邮件正文只按 ASCII 传送时会受到字符集和二进制内容表达能力限制。

服务器响应码帮助客户端判断当前命令是否接受。课堂示例提及常见成功响应 `250`，以及服务器允许客户端开始输入邮件数据时返回 `354`（44:07–44:48）。读取协议交互时不要只看代码数字，还要结合它出现的位置：`354` 表示可以开始提交数据，并不表示整封邮件已经投递完成；传输结束后仍需服务器确认并正常关闭会话。

邮件数据部分通常包含头部和正文，两者由空行分隔。头部可带发件人、收件人、日期和主题等字段；正文包含邮件的主要文本或 MIME 组织结构。SMTP 会话结束标记与正文普通字符之间必须依协议规则区分，否则服务器无法确定消息内容已经结束。课堂提及用回车换行后接句点再回车换行表示数据结束（44:43–45:27）；这属于协议层消息边界表示。

### To、Cc 与 Bcc 的可见性

`To` 指明主要收件人；`Cc`（carbon copy）向其他收件人提供可见副本，收件人通常能看到该邮件也抄送给哪些地址。`Bcc`（blind carbon copy）向额外收件人发送副本，但一般不会把这些地址展示给其他收件人。教师用小组通知说明，`Cc` 是公开可见的抄送，`Bcc` 则不让主要收件人看到密送对象（46:00–46:45）。

这些字段的显示和传送仍需与 SMTP 信封区分。邮件头用于描述消息及呈现给用户的信息，传输信封用于指示服务器实际投递对象。密送地址若直接暴露在交给所有收件人的头部内容中，就违背密送目的，因此系统需要在投递与展示时妥善处理。用户在不同客户端查看已发送邮件时，可能看到自己设置的密送记录；收件人看到的副本则未必包含相同信息。

### POP3 与 IMAP 的使用情形比较

POP3 的课堂模型是用户连接服务器并下载邮箱消息，下载后服务器上可能删除副本。若用户只用一台电脑，离线保存邮件较直接；若同时用多台设备，某设备下载并删除后，其他设备可能无法再从服务器取得相同内容。课堂还指出，早期 POP3 客户端可能按顺序下载邮件，大附件阻塞后续邮件处理（47:12–48:49）。现代客户端可以通过设置保留服务器副本等方式改变使用体验，所以应把课堂协议特征与具体软件默认行为区分。

IMAP 保持邮箱以服务器为中心。客户端可先查看邮件列表和首部，按需下载正文或个别附件，也能在不同终端间同步邮箱状态（48:54–50:11）。代价是联网读取时依赖服务器连接；客户端若将邮件完整缓存到本地，也能提供一定离线能力。比较 POP3 与 IMAP 时可从邮件保存在何处、是否适合多终端同步、是否支持按需取附件、断网时可访问程度等方面说明，不把“下载”和“服务器删除”绝对化为所有客户端环境都相同。

### SMTP、POP3 与 IMAP 的端口与方向

课堂将 SMTP 与 TCP 25 端口联系起来，并说明邮件读取协议也通过 TCP 客户端/服务器通信（43:34–44:02、46:51–47:10）。课堂重点是区分协议所负责的阶段：SMTP 用于提交和转发，POP3 与 IMAP 用于收取。现实系统还可能使用加密连接及其他服务端口，端口配置依服务设置而异；如果题目要求课堂端口识读，按教师给出的端口作答。

简化地看，一封邮件从撰写到阅读可经历：用户代理提交给发件服务器、发件服务器通过 SMTP 向目标域的邮件服务器投递、接收服务器存储邮件、收件客户端通过 POP3 或 IMAP 读取。每段都有独立连接和责任边界。传输成功不保证收件人已经阅读，客户端读到列表也不一定表示所有附件已经下载。
