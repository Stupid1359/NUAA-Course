# 计算机网络｜2026-10-21 第3节

本节继续第四章网络层。前段复习 BGP，讲路由器的控制与转发；主体说明 IP 多播、IGMP、组地址映射及多播路由；后段讲 VPN 的访问范围与隧道，最后引出 NAT。课尾提到考试安排已有消息，但本节转写没有给出完整日期地点；下一节教师再次核对了具体信息。

## BGP 回顾与路由器的两项工作（00:33–06:43）

教师开课时短暂复习 BGP 与 AS 路径，随后转向路由器本身（01:41–03:24）。路由器连接不同网络，通常每个参与转发的接口处于相应网络中。它一方面运行路由选择协议，形成到目的前缀的路径认知；另一方面接收分组、查表、从正确的输出接口发送。控制信息决定表的内容，数据转发使用表的结果（03:24–05:24）。

课堂把路由器视为执行专门任务的计算机：有多个输入和输出端口，中间有交换结构，控制部分维护路由表（03:50–04:58）。路由选择处理机根据域内或域间协议更新路由，端口上的转发表支持快速查找。教师指出，本课程答题时不要求把“路由表”和“转发表”的术语作严格区分，写“按照路由表转发”可以接受（05:26–05:42）。学习机制时仍要知道路由选择与每个分组的发送发生在不同环节。

补充过程：假设 R 的控制部分获知前缀 `203.0.113.0/24` 应经接口 2 的邻居 X 到达。数据报到达接口 0，转发部分用目的 IP 匹配前缀，在转发表中选择接口 2，准备下一链路的帧并发送。若控制部分随后获知接口 2 故障，转发表需要随路由变化更新；在更新完成前到达的分组，可能仍受旧表影响。这个例子说明转发依赖控制结果，但控制协议不会替每个数据报逐一计算完整路径。

路由器的输入端口要处理物理信号、链路帧和网络层分组；输出端口也要完成相应层次的发送处理（06:43–07:57）。在一跳结束时，原链路帧已经完成本链路的任务。路由器向下一跳发出分组时，需要重新封装该下一段链路上的帧，重新确定本段的源与目的 MAC 地址，并重新计算帧检验序列。目的 IP 通常继续表示最终接收方；链路层地址则随每一跳变化。将这两组地址分开，才能解释“IP 数据报跨越多个以太网段”如何实现。

## 路由器排队、丢弃与交换结构（08:00–10:35）

分组进入速度超过处理或出口发送能力时，输入与输出队列都可能拥塞；队列容量有限，路由器需要选择丢弃哪些分组（08:00–08:35）。课堂以实时视频和文件传输对照说明，业务的时效要求不同，丢弃策略的影响也不同。实时视频中的旧画面如果已错过播放时刻，晚到后价值可能很低；可靠文件传输需要维持文件内容完整，丢失的数据通常依赖传输协议重发（08:35–09:44）。

这段例子是在说明取舍，不能据此推出“所有视频设备一律丢旧包”或“所有文件数据绝不丢包”。实际队列管理还要考虑协议、时延预算、优先级、重传机制与公平性。比如 TCP 文件传输发生丢包后，发送方可能重传并调整发送速率；如果分组原本处于输出队列，路由器并不知道应用层文件的全部语义。课堂要求的是理解排队与丢弃会影响不同业务，而非记忆一条通用丢弃命令。

输入端口与输出端口之间有交换结构。教师列出通过存储器、总线和纵横交换结构三种方式（09:45–10:23）。存储器方式涉及从输入写入、再由输出读取；总线方式需要共享传输资源；纵横结构为多组输入输出提供更灵活的并行连接机会。性能分析时要说明瓶颈位于何处：单一共享资源可能限制同时交换的数量，多个端口同时繁忙时队列也可能增长。教师没有展开硬件细节，课堂关注的是认识三类实现及它们在路由器内部承担“输入到输出”连接任务。

补充数量例子：某出口每秒最多发送 1000 个等长分组，输入端一秒内送来 1500 个并且没有其他出口可分担，至少有 500 个分组需要排队或被丢弃。即使内部交换结构非常快，出口速率仍然限制发送量；若输出可以发送而输入队列已经拥塞，瓶颈又可能转移到输入处理。判断拥塞位置必须看实际到达率、服务率和队列长度，不能仅凭“路由器性能高”判断没有丢包。

## 多播为何节约链路资源（10:36–14:14）

IP 多播面向一组自愿加入的接收者，完成“一份内容发送给多个接收点”的任务（10:42–11:24）。教师用 90 台主机观看同一视频的例子说明：逐个单播时，靠近服务器的公共链路可能重复传送 90 份内容，后续分叉处仍会出现多份内容；多播则让共享路径上传送一份，到需要分叉的路由器处再复制（11:24–13:00）。接收者数量越多、路径共享程度越高，节约的链路传输量通常越明显。

把课堂例子写成简单算式：若视频流速率为 $b$，有 $n$ 个接收者，并且他们共享一段主干链路，逐个单播可能要求该段承载约 $n b$ 的同内容流量；多播在该段只需约 $b$ 的数据流量，另有组管理和路由控制开销。若 $n=90$ 且 $b=2\,\mathrm{Mbit/s}$，该共享段的单播同内容流量可达约 $180\,\mathrm{Mbit/s}$，多播数据约为 $2\,\mathrm{Mbit/s}$。这是课堂场景的说明性计算，真实网络中的链路布局、协议开销和是否支持多播都要另外考虑。

多播数据报的目的 IP 是组地址，不把所有接收主机的单独 IP 地址列入一个分组（12:22–12:41、14:14–14:49）。运行多播路由功能的设备可以和普通单播路由器是同一台物理设备，只需增加对多播组及转发路径的处理能力（13:00–13:45）。同一设备承担两种转发任务，不代表单播路由表天然包含所有多播组的转发结果。组成员动态加入和退出，还要求相应的状态维护。

教师说明 IPv4 的 D 类地址用作多播组地址；其最高四位为 `1110`，地址范围从 `224.0.0.0` 起（14:14–14:49、19:36–19:43）。多播组地址用在分组的目的地址字段，源地址仍用于标识发送者。某主机可以向组发送数据，即使它自己没有加入该组；发送资格与接收成员身份属于不同问题（25:26–25:41）。

**【理解重点】多播节约资源的关键发生在共享链路：在路径分叉点按需要复制。**若一条链路上重复发送多份相同内容，接收者越多越容易占满公共传输资源。另一方面，多播仍需维护组成员和路径状态，它节约数据流量并不意味着完全没有控制开销。

## IGMP：主机与邻近路由器的组成员关系（14:50–17:51；22:32–26:27）

主机要接收某组的数据，需要让邻近的多播路由器知道本地网络中有该组成员。课堂把主机与最近路由器之间的成员管理归于 IGMP，指出 IGMP 直接承载在 IP 数据报内，IPv4 `Protocol` 字段值为 2（14:50–15:56）。这段信息的作用是维护“某条本地链路上是否有接收者需要这个组”，不负责在整个互联网中寻找多播传输路径。

教师强调路由器关注某组在本地网络中是否仍有成员，不必记录每个加入者的精确人数（16:05–16:40）。设同一局域网有三台主机属于组 G，路由器转发时只需知道“此局域网有 G 成员”，便可向这一链路发送一份 G 数据报；链路上的相应主机再接收。若其中两台退出，只要还剩一台，路由器仍需向该局域网发送；如果全都退出，就可以停止向该链路转发组数据。

IGMP 通过主机报告与路由器查询维护成员状态。课堂介绍旧版本中主机退出后未必主动报告，路由器需要定期查询；较新的版本可以主动报告退出，但仍需查询机制处理消息丢失和异常离线（16:40–17:36）。查询不只为统计人数，更用于验证某组在链路上是否仍有至少一名成员。教师在 25:45–26:27 再次归纳两个阶段：主机发起加入，路由器随后通过查询探知成员状态变化。

补充判断题：主机 H 向组 G 发送一份视频分组，H 没有加入 G；在接收网络上有两台主机加入 G。该分组仍可被路由器向接收网络转发，因为源主机是否加入并非发送的必备前提。接收网络的路由器也只需知道“存在 G 成员”，无需为了发送一份组数据先统计具体的两台主机。若接收网络所有成员离开，路由器经过相应确认后停止向该链路发送 G 数据，主干路径也可能随成员变化调整。

IGMP 解决本地成员管理，多播路由协议解决路由器之间如何把数据送往需要它的网络（22:32–24:34）。把 IGMP 当作整个 AS 的多播路由协议，会无法说明路径分叉、来源检查以及其他路由器如何学习转发方向。课堂对 IGMP 各版本没有展开详细状态机，讲义也只使用本节可核实的共同流程。

## IP 多播组地址到以太网地址的映射（17:51–22:32）

多播分组跨网络传送时，路由器依据 IP 多播目的地址和多播路径决定下一段方向；进入最终以太网链路后，还需要相应的以太网多播目的地址，供链路接收设备识别（17:51–18:58）。教师讲解 IPv4 多播地址映射时指出：以太网多播地址前 25 bit 固定，后 23 bit 取自 IPv4 多播目的地址的低 23 bit（18:59–20:34）。常见的以太网前缀可以写为 `01:00:5e`，其后部分还要按固定的高位 0 与 IP 低 23 bit 组合。

IPv4 多播地址最高四位固定为 `1110`，可变化的组地址位数为 28；以太网映射只保留其中 23 位。因此有 5 位不进入映射，可产生 $2^5=32$ 个 IPv4 多播地址对应同一个以太网多播地址的可能情形（19:36–20:55）。这个 $32:1$ 描述的是地址映射空间的最大重合数，不表示某次通信已经有 32 个组同时活跃，也不表示每台主机都会收到 32 个组的数据。

补充示例：`224.0.0.1` 的低 23 bit 与另一个在被忽略的 5 位上不同、低 23 bit 相同的组地址，可以映射到同一以太网多播地址。网卡可能因为相同的链路目的地址接收帧，但主机的 IP 层仍要检查分组的目的多播 IP，判断自己是否加入相应组。故“链路层收到了帧”和“应用可以接收该组数据”之间还有网络层的成员检查。

教师给出的误收条件有两个：主机处于同一子网，其中存在不同多播组的接收者；这些不同组地址的低 23 bit 相同（21:25–22:29）。前一条件使以太网多播帧能够到达同一链路上的设备，后一条件使不同 IP 组使用同一以太网多播地址。网络层的再次过滤负责排除自己没有加入的 IP 组。做地址映射题时，先取 IPv4 目的地址的低 23 bit，再组成以太网地址，最后讨论可能的重合；不要把整个 32 bit IP 地址直接填进 48 bit 以太网地址中。教师在 36:11–37:41 的课堂答题中特别提醒掌握这一步。

## 多播转发路径与源地址检查（22:32–31:53）

多播路由的目标是使数据到达所有需要它的组成员网络，同时控制重复转发。与单播路由只寻找某个目的地址的一条或若干下一跳不同，多播以源或共享核心为起点形成一棵分支路径；同组成员的加入与退出会改变哪些分支有必要保留（22:32–28:02）。同一个组如果有多个数据源，基于源构建的转发路径也可能不同。

教师强调，多播转发除了组目的地址，往往还要检查报文来自哪里（25:07–25:26）。反向路径检查可以利用到源的单播路由信息：路由器先看“如果我要到该源，最合适的出接口是哪一个”，再检查组数据是否从对应接口进入。若来源接口与预期不符，这份组数据可能来自绕行或重复分支，可以抑制转发（28:38–30:01）。这项检查帮助阻止同一源分组沿环路进入同一转发分支。

补充示例：R 从接口 A 到源 S 的最短路径代价为 2，从接口 B 到 S 的最短路径代价为 5。源 S 的同一多播分组分别经 A、B 到达 R。按反向路径检查，R 接受从 A 到达的副本并向合适的下游接口转发；B 的副本不再继续传播。这里查看的是到源 S 的反向路径，组地址仍用于判断哪些下游网络需要接收。若路由政策或等价路径使选择不同，具体规则应按多播协议的设定执行。课堂口述在等价情形下可用来源 IP 的顺序确定唯一选择（29:40–29:56）。

洪泛初期可能使许多分支收到数据，随后根据组成员情况剪去没有接收者的分支；新成员加入时还可以把必要分支接回转发路径（30:01–31:53）。教师用“洪泛与剪除”解释这一过程。判断某分支是否有用，不能只看当前这台路由器上有没有本地组成员，还应看它的下游是否有其他组成员。若下游还有接收者，剪掉该分支就会使那些接收者失去数据。

**【理解重点】一条多播路径服务的是一组接收者，发送数据的源主机可以在组外。**对某个组及某个源的转发状态，应包含进入方向和需要复制到哪些下游方向。若同一份数据在环中重复流动，可能消耗带宽并造成重复接收；反向路径检查与剪除都围绕这一问题发挥作用。

## 隧道、共享核心与多播协议选择（31:53–37:42）

若中间一段网络设备不支持多播，教师建议用隧道连接两段支持多播的网络（31:53–33:13）。隧道入口把原始多播 IP 数据报当作负载，外加一层面向隧道出口的单播首部。中间网络按外层的单播目的地址转发；出口去除外层首部，恢复内部多播数据报，继续按多播规则处理。内层多播组地址代表真实接收组，外层单播地址只用于跨越不支持多播的区段。

补充长度问题：若原始多播 IP 数据报为 1200 B，外层增加无选项 IPv4 首部 20 B，隧道中的数据报至少为 1220 B。若路径 MTU 小于封装后的长度，需要按隧道与 IP 的分片或路径 MTU 规则处理；“隧道能转发”不等于“封装后仍适合任意链路 MTU”。出口恢复的原始目的地址仍是组地址，不会因为外层单播路径而改变接收组。

多个源各自建立一棵多播树可能带来维护开销。基于核心的方式选定一个共享点，各源先将数据送到核心，再由核心使用共享的分支结构向接收者转发（33:13–34:26）。例如三位参会者轮流发言，若每人分别维护一棵面向相同听众的树，需要维护多个源相关状态；共享核心让源先汇集，随后使用共同的分发结构。采用核心也引入路径绕行与核心容量的考虑，实际协议根据接收者分布及业务目标选择。

教师列出多播路由协议可以基于不同单播路由信息实现，并提到协议无关多播与稀疏、密集分布（34:26–36:10）。这里的“协议无关”指它能够利用已有单播路由信息，而不绑定某一个特定的单播路由协议。稀疏表示组成员分散，许多网段可能没有成员；密集表示成员分布集中，更多相邻网络需要接收。课堂用集中在线上课与分散用户作对照。不同分布会改变“先广泛发送再剪除”与“按明确加入需求建立分支”等方法的成本，课程没有要求记忆具体多播协议的完整状态机。

## VPN 的范围、访问授权和隧道（37:42–48:31）

教师把 VPN 放在组织网络和访问控制的语境中讲解。一个机构可以经公共网络把相隔的校区或部门连接起来，对内部资源设置认证、授权与加密传输，形成逻辑上的专用通信范围（37:42–40:54、43:43–44:44）。VPN 解决的是“谁能够访问哪些内部资源，以及经过公共网络时如何保护通信”；地址数量不足则是 NAT 要处理的另一项问题。两项技术可以同时出现，但部署 VPN 并不规定内部网络必须全部使用某一类私有地址。

课堂区分三种接入场景：机构内部网络成员访问内部资源，合作方获得有限资源访问权，以及个人在外部远程接入组织网络（40:55–42:13、47:54–48:31）。教材对应的英文术语可写为 `intranet`、`extranet`、`remote access`。例如同一学校两个校区之间连接，可属于机构内部访问；外部合作单位只获准访问某些服务，属于受限的外部机构访问；学生在校外经授权访问馆藏资源，属于远程访问。场景不同，授权范围与身份管理也应分别配置。

教师特别解释，私有 IP 地址、NAT 与 VPN 的概念不能互相代替（38:52–40:54）。私有地址在本地范围可重复使用，通常无法在公共互联网直接作为全局可达地址；NAT 在边界改写地址；VPN 可通过隧道及身份与加密机制保护机构之间的通信。某网络同时使用三者是常见组合，但“看到 `192.168.x.x` 地址”本身只能说明该地址属于私有地址范围，无法证明通信经过 VPN。

课堂例子把两个校区的边界设备作为隧道两端（45:31–47:50）。内部 IP 数据报在进入公共网络时被保护并封装，外层首部携带隧道两端可达的地址；到另一端后，边界设备验证并恢复内部数据，再继续在本地网络转发。加密和解密需要相应协议、密钥与设备配置；隧道的外层转发本身不自动提供机密性。分析一张 VPN 封装图时，分别标记内部源目的地址、外部隧道端点地址以及加密覆盖范围，便能说明每一段设备看得见什么信息。

教师提到可在不同层次实现保护机制，包括网络层的 IPsec（46:37–46:58）。这里的重点是理解安全机制放在何处会影响哪些字段受到保护，不能把“存在隧道”直接当作全部数据已经加密。若题目要求判断公网路由器的转发依据，它依据的是外层可路由地址；若题目要求判断机构内部通信双方，则看解封装后的内部数据报。

## NAT 引入：私有地址与全球地址（48:31–51:07）

教师随后引出 NAT。IPv4 全球地址资源有限，NAT 使内部地址通过边界设备转换成可在外部网络使用的地址（48:31–49:52）。基本情形要求 NAT 路由器至少有一个可用的全球地址；内部主机的出站数据经过边界时，其源地址被改写为对应的外部地址，回程数据再依转换记录找到内部主机。下一节会继续讲地址池、端口转换及往返过程。

课堂示例中，内部主机为 `192.168.0.3`，外部地址为 `172.38.1.5`（50:20–51:07）。`192.168.0.3` 属于私有地址范围；`172.38.1.5` 的第一字节虽为 172，却不在 `172.16.0.0/12` 私有范围内。判断地址是否属于私有范围要检查完整前缀，不能只看它是否以 172 开头。对于 `172.16.0.0/12`，第二字节从 16 至 31；32 及以上已超出这段范围。教师也用这个例子提醒学生按地址段判断（50:42–51:03）。

补充出站步骤：内部主机向外部主机 B 发送数据，源地址为 `192.168.0.3`，目的地址为 B；NAT 设备把源地址转换为 `172.38.1.5`，将对应关系保存。B 回复时目的地址是 `172.38.1.5`，NAT 设备根据记录把目的地址恢复为 `192.168.0.3`。若没有相应记录或静态规则，设备无法仅凭一个公网地址无条件判断该送给哪台内部主机。该例子的完整回程讲解见下一节。
