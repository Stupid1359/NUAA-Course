# 计算机网络｜2026-10-23 第3节

本节前半段完成第四章网络层的 SDN 和复习，30:30 明确开始第五章运输层，随后讲进程通信、TCP/UDP、端口及套接字。字幕在少数术语上有识别误差，讲义采用课程语境中的规范英文名称；涉及课堂要求的原话保留转写文本。

## SDN 控制器的组成与接口（00:52–07:37）

开课签到后，教师接续上一节介绍 SDN：控制层面由控制器负责网络范围内的策略和状态管理，数据层面的交换机按收到的流表转发（02:16–03:07）。控制器的通信部分同受控交换机交换信息；核心管理部分汇集链路、端口、设备与流量状态，并据此形成流表；上层应用通过接口读取统计信息或提出管理要求（03:09–05:47）。把三个部分连起来看，能够解释一条规则从应用意图到交换机动作的传递路线。

南向接口连接控制器和受控设备，课堂以 OpenFlow 作为典型协议，并提到 SNMP 能协助收集设备运行状态（03:30–04:11）。北向接口向管理应用提供访问控制器能力与统计信息的 API，课堂指出这类接口随应用需求变化，没有单一的课堂指定形式（05:02–05:37）。若应用要求限制一类流量，控制器需要把要求转化为设备可执行的匹配条件与动作；若设备状态发生变化，控制器还需要依据收到的信息更新相关规则。

教师在 06:46–07:16 特别澄清 SDN 与 OpenFlow 的关系：OpenFlow 是一种典型南向通信方式，SDN 可通过其他技术实现。掌握这一点有助于阅读术语：看到“OpenFlow 交换机”可推断其遵循相应协议；看到“SDN 网络”只能推断控制方式，不足以确定设备全部使用某一个协议版本。课堂提到 OpenFlow 1.3、1.5 等版本，但明确不展开版本演进（07:23–07:37）。

补充场景：一个交换机的 3 号端口开始持续拥塞。设备上报端口统计信息后，控制器判断部分流量可改经另一条路径，于是给相关交换机发送新表项。后续符合规则的分组按新表项走。这里需要控制器知道可用路径，也需要交换机能够识别相关流；仅在控制器界面显示“拥塞”不会自动改变分组路径。

## OpenFlow 流表的匹配、动作和计数（07:39–14:06）

OpenFlow 交换机处理分组时，先从收到的帧与协议首部提取匹配字段，再查询流表，最后执行相应动作（07:39–08:57）。字段可来自输入端口、链路层 MAC 地址与类型、网络层 IP 地址以及运输层端口。具体实现支持哪些字段由设备和协议版本决定。传统目的前缀查询只是这类匹配中的一种较窄情况；课堂强调流表能够组合多个层次的信息（09:04–09:49）。

一个表项可分为匹配条件、动作与统计信息。匹配条件回答“哪些分组使用这条规则”，动作回答“匹配后怎样处理”，计数器记录匹配次数等运行信息（09:51–10:58、12:03–13:55）。动作可以是向指定端口转发、丢弃、改写某些字段，或者将必要信息交给控制器继续决定。没有匹配项时，设备可能按预设规则丢弃或向控制器请求处理，不能假定所有未知分组总会被自动允许（13:00–13:33）。

通配条件表示某一字段不限制取值。例如规则“输入端口 2、目的 IP 前缀 P、其他字段任意，输出端口 4”，只要求输入端口与目的前缀满足条件；源 MAC 与源端口变化仍可以匹配（13:00–13:18）。若在同一交换机还设置一条更宽的规则，应理解表项优先级及匹配次序，否则同一个分组可能同时符合多条规则。转写没有给出完整的优先级设置图，因此解题应以题目提供的表项和处理顺序为准。

计数器和表项有效期帮助控制器判断规则运行情况。教师提到可以统计某表项用于转发的次数，也要关心表项持续多久以及是否继续有效（12:16–14:02）。例如某条临时流表项服务于一段文件传输，传输结束后仍长期占用设备空间就没有必要；但过早删除，又可能让后续分组重新上报控制器。实际超时策略由设备配置决定，课堂主要要求认识统计与有效期的用途。

补充计算：假设一条表项每秒平均匹配 2000 个分组，10 秒后计数器新增 20000。这个数字反映“规则被使用的次数”，并不能直接说明字节吞吐量；若每个分组长度不同，还需要累计字节数才能估算流量。若某规则的分组数始终为零，可能是没有相关流量、匹配条件写得过窄、路径没有经过该设备，或另一条优先级更高的规则先处理了分组，不能只凭零计数认定设备损坏。

## 用流表实现指定路径和流量安排（14:06–19:05）

课堂用三台交换机 S1、S2、S3 和主机 H3、H4、H5、H6 说明“策略路径”如何落实到每台设备（14:06–18:08）。教师规定 H5、H6 到 H3、H4 的分组走 S3→S1→S2。控制器要为路径上的每个交换机设置相关规则：S3 将符合源和目的条件的分组送往 S1，S1 继续送往 S2，S2 再依据目标主机选择接入端口。只配置入口交换机无法保证中间设备按指定路线继续转发。

课堂特别指出一个匹配范围问题：若把 H5、H6 的具体地址概括成整个 `10.3.*` 网络，规则会让该前缀内其他主机也受影响（15:32–17:40）。题目若只要求“这两台主机应走此路径”，范围较宽的表项可能满足其最低要求；题目若明确要求“只有这两台主机”，就必须精确到相应地址，或增加能排除其他来源的字段。判断规则是否正确，要检查其覆盖的分组集合，不只检查教师举出的两个样本是否能匹配。

可把这点形式化。设期望集合为 $T=\{H5,H6\}\times\{H3,H4\}$，某流表规则实际覆盖集合为 $M$。若题目要求“指定分组走该路径”，至少需 $T\subseteq M$ 且相关设备动作正确；若题目要求“恰好这些分组”，则需 $T=M$。将源条件写成一个整个网段，通常使 $M$ 包含该网段更多主机。这个集合分析是讲义补充说明，对应课堂 15:41–17:29 关于规则覆盖范围的讨论。

教师又以来自 H3、H4 的流量走不同路径说明负载分配（18:08–19:05）。在 S2 区分两股流量，可以使用不同输入端口或源地址等条件，再为它们指定不同输出端口。具体要选哪一字段，应看网络连接图：若两个来源可能经同一输入端口到达，仅用输入端口就不能区分；若源地址可以清楚地区别，加入源地址条件更可靠。

## 流表中的允许规则与拒绝规则（19:05–21:15）

课堂接着以 S2 限制接收来源为例，说明“写了允许”与“完成全部限制”需要分别检查（19:05–21:06）。如果只写“来自 S3 方向、源地址属于 `10.3.*` 的分组可转发到 H3/H4”，规则只说明这些分组如何处理；它还没有直接说明其他输入方向上的同类源地址怎样处理。若题目要求排除从 S1 方向冒用该源地址的分组，需要结合默认处理规则或增加明确的拒绝表项。

补充检查方法：列出每个相关来源场景和期望动作。例如“从 S3 方向进入且源在允许范围内：转发”，“从 S1 方向进入但声称源在相同范围内：丢弃”，“其他合法流量：按其他表项处理”。再逐行测试表项是否覆盖场景，是否有优先级冲突。若允许范围只有一个前缀，不能由这一条表项推断设备已经阻止所有未授权输入；完整结果还取决于未匹配分组的默认动作。

这段也是理解 SDN 安全策略的关键：一个策略往往需要正向允许和其他情况的处理规则共同表达。通配条件扩大规则范围，精确条件缩小规则范围；两者都可用于正确设计，但必须与目标范围一致。教师在 21:06–21:15 结束这部分介绍，随后转入第四章复习。

## 第四章复习：地址、报文、路由与新技术（21:15–25:40）

教师明确把 IP 地址分配、路由条目匹配列为第四章需要灵活计算的内容，并说明练习题覆盖多种题型（21:17–21:51）。做地址题时应先写前缀长度与地址块边界，再检查需求量、块容量与各块是否重叠。做转发表匹配题时应把目的 IP 与每个候选前缀按位匹配，多个候选同时符合时依据最长前缀选择。若用 VLSM 分配机构地址，先按所需主机数量确定块大小，最后检查总块范围是否落在上级前缀内。

教师要求能够识读给出的 IPv4 首部结构，并在分片题中正确处理 Identification、标志位、Fragment Offset 等字段（21:52–22:21）。补充例子：原 IP 数据报有效数据 2800 B，无选项首部 20 B，出口 MTU 为 1500 B。每个非最后分片最多放 $\lfloor(1500-20)/8\rfloor\times8=1480$ B 有效数据；因此第一片放 1480 B，第二片放 1320 B。两片总长度分别为 1500 B 与 1340 B，Fragment Offset 分别为 0 和 $1480/8=185$，前片 MF 为 1，末片 MF 为 0。原始数据起始字节与字段中的 8 B 单位数值须分别计算。

ARP 需理解本地链路上 IP 地址与 MAC 地址的解析关系；IP 转发过程要能够说明下一跳如何确定，但教师说不要求默写整段流程（22:24–22:39）。CIDR 练习包括地址块分配、路由聚合。聚合时只保留各待聚合前缀真正共同的高位，其他位写零；若聚合结果覆盖了额外地址，还需判断题目是否允许向这些地址通告一条更宽的路由。简单地把两个网络地址按十进制平均，无法得到正确聚合前缀。

RIP 与 OSPF 要理解路由更新或路径计算；RIP 的邻居通告题要求会计算，OSPF 的图题要求能根据拓扑求出以某路由器为起点的最短路径结构（23:10–24:49）。BGP 的要求相对集中于自治系统之间的可达性与策略。教师明确说第四章一般会出大题（24:28–24:38）。对 IPv6、VPN、NAT、MPLS 和 SDN，课堂分别强调概念、地址转换过程、标签交换流程及 OpenFlow 的基本作用（24:49–25:37）。复习时要按教师给出的程度处理，不把概念介绍扩写成未经说明的考试范围。

**【考试要求】第四章的地址、分片与路由计算要能独立完成，教师明确说本章一般有大题。**（21:17–25:37）题目中的数字、图和前缀需要逐项计算；仅写结论可能无法说明选择依据。完整原话及程度见文末考试事项。

## 第三章作业讲评与第五章交接（25:40–34:25）

教师说第四章作业已放在学习通，部分同学已经提交，提醒按时完成（25:40–25:48）。随后讲评第三章已批改作业的共性问题。第 27 题涉及多个站点共享带宽，计算出的数值需注明“共享时的平均带宽”，单个站点空闲时可能得到更多资源（25:48–26:53）。第 33 题涉及交换机自学习，逐步记录“当前事件新增了哪条表项”即可，不必每一步把此前所有表项重写（26:53–28:21）。

第 16 题把码元速率的单位误写成 `bit/s` 会混淆波特率与比特率。若每个码元承载 $k$ bit，二者满足 $R_b=kR_s$；仅在 $k=1$ 时数值才相等。应根据题目究竟询问码元每秒还是比特每秒选择单位（28:25–28:53）。第 30 题最大吞吐量需要同时考虑跨路由器通信和各系内部通信，教师指出只写一个数字无法知道计算过程；投影完整拓扑未进入转写，讲义不重建其原题结果（28:53–29:55）。第 7 题的 CRC 生成与校验也要先读清题目给的是原数据还是已附检验序列（29:57–30:21）。

30:30 教师明确开始第五章运输层，并说明 TCP 是本章重点。运输层位于应用与网络之间，需要让不同应用进程得到适合的传输服务。网络层可把 IP 数据报送到目的主机，运输层还要将数据交给目的主机内正确的应用进程（30:30–38:42）。这一交接解释了后续为何需要端口：主机上网页、邮件和其他程序可以同时使用网络，目的 IP 只能定位主机，目的端口才帮助定位正确的接收者。

教师以邮件和音视频说明业务需求：邮件强调完整到达，实时音视频更关注播放连续性和时延，对少量画面数据损失的容忍度可能较高（32:31–34:17）。这只是业务目标的例子，实际应用协议仍可能增加自己的重传、缓冲或错误恢复机制。选 TCP 或 UDP 时应问“应用能否等待重传、是否需要接收顺序、是否需要多播、是否自行处理可靠性”，不能只按名称判断所有音视频都采用同一传输方式。

## 进程通信、复用与 TCP/UDP（34:25–43:42）

教师把运输层称为应用进程之间的逻辑通信通道，而网络层承担主机之间的交付（34:25–37:17）。发送端的多个应用把数据交给运输层，接收端依协议和端口把数据分给对应应用，这分别是复用与分用（37:17–38:42）。路由器通常只需根据 IP 转发分组，不替端系统决定每个应用进程如何处理负载。若某主机上浏览器正常而另一程序访问失败，需要分别检查应用服务、目的端口及通信路径，不能仅从一个程序可用推断所有进程均可用。

TCP 提供面向连接、可靠、全双工的字节流服务；UDP 提供无连接的数据报服务，保留应用报文边界，可靠性机制由应用按需补足（38:43–40:29）。TCP 的协议数据单元称为 segment，UDP 的称为用户数据报。教师提醒术语中的“数据报”也会用于网络层，需要看上下文区分是 IP 数据报还是 UDP 用户数据报。TCP 的一条连接连接两个端点，因此单条连接用于一对一通信；UDP 可以作为 IP 多播数据的运输承载（40:29–41:27）。

补充对比：一台视频服务器要给 50 个用户送相同内容，若为每个用户建立一条 TCP 连接，会形成 50 条独立连接和相应状态；若网络和应用都支持多播，可用 UDP 承载组数据并通过多播路径共享公共链路。不过 UDP 不提供 TCP 的确认和按序字节流，应用是否能接受部分丢失须自己决定。用户人数、服务要求和网络支持情况共同决定采用哪种方式。

教师列举 DNS、DHCP、RIP 与 UDP 的关联，HTTP、SMTP、FTP 与 TCP 的关联（41:28–43:42）。这些是课程中常见的协议组合，具体应用实现可能有不同版本或附加协议。尤其网页登录邮箱时，浏览器与网页服务之间的交互和邮件服务器之间的发送是不同通信过程，不能凭浏览器界面就把全部邮件传递称为 HTTP。运输层所关心的是把相应报文交给正确应用进程，并按所选协议提供相应的服务。

## 端口号、套接字与端点识别（43:42–51:40）

端口号为 16 bit，范围是 0–65535；TCP 与 UDP 各自有端口空间。课堂以客户端端口 58800、服务端端口 80 的网页交换说明：请求的源端口是客户端端口，目的端口是服务端口；回应时两者方向相反（44:40–45:35）。端口属于本地主机的协议端点标识，另一台主机也可使用同一个数字。端口并不等于路由器上插网线的物理接口（45:35–46:31）。

教师把端口分为熟知、登记和临时分配三类，用“小于 1k”“约 1k 到 48k”“48k 以上”作课堂记忆界线，并说具体端点数字不要求逐一背诵（46:32–50:54）。这是一种课堂化记忆方法；具体标准范围、系统临时端口区间和应用默认端口要看实际注册表及主机配置。服务端可以配置其他端口，但访问方须知道相应地址与端口。若连接到 `example.org:8080`，目的端口就是 8080，不能仍按默认 HTTP 端口 80 猜测。

补充说明：IP 地址标识通信主机的网络接口，端口帮助标识主机上的服务端点；`(IP,port)` 可以表示一个套接字地址。一个 TCP 连接通常需要源 IP、源端口、目的 IP、目的端口和协议种类来区别于其他通信。端口 80 可以同时出现在不同服务器或不同 TCP 连接中，因为另外的地址与端口成员使连接身份不同。教师在下一节还会继续讲端口与套接字的用法。

**【理解重点】端口标识本地主机的通信入口，完整连接还要结合双方地址、双方端口与协议。**（44:17–46:31）例如同一客户机同时访问两个不同服务器的 80 端口，目的端口相同，目的 IP 不同，仍属于两条不同连接。

### 把主机交付与进程交付连成一次完整通信

补充说明：设客户机地址为 `192.0.2.10`、临时端口为 50000，服务器地址为 `198.51.100.20`、服务端口为 80。发送时，应用把请求交给运输层，运输层写入源端口 50000、目的端口 80；网络层写入源 IP 和目的 IP；链路层把数据送向本地下一跳。中间路由器逐跳更换链路帧，依据目的 IP 选择下一跳。到达服务器后，IP 层确认目的地址属于本机，运输层依据协议和目的端口 80，把有效数据交给正在服务的应用。

回应时源 IP、源端口分别变成 `198.51.100.20`、80，目的 IP、目的端口分别变成 `192.0.2.10`、50000。两次传送使用同一对通信端点，但每个方向上的“源”与“目的”互换。若客户机同时打开另一个网页，操作系统可以使用另一个临时端口；即使两个请求都发往同一台服务器的 80 端口，服务器仍能依连接的完整端点信息区分它们。这个例子也说明为什么仅依据 IP 地址无法把回应交给某一个浏览器连接。

课堂把端口与进程联系起来，是为了说明分用目标；具体操作系统内部可能由套接字、文件描述符、监听套接字与已建立连接套接字共同组织。应用进程也可能同时管理多个连接，因此“端口号”和“进程 ID”不能当成同一个编号。一个服务进程监听某个端口，可以同时为多个客户连接提供服务；每条连接仍由双方地址和端口区分。理解这一点后，后续 TCP 建立连接、接收缓存和窗口管理中的“每条连接”才有明确对象。
