## 目的地址查表与最长前缀匹配（01:07–07:31）

### 主机本地判断与路由器查表

教师接续上节例题：主机 H1 先把目的 IPv4 地址与自己的子网掩码按位与，得到在自己掩码下的目的网络地址，再与自身网络地址比较；若不同，就把数据报交给 R1（01:07–02:11）。R1 查询自己的路由表，每一行具有自己的前缀长度或掩码。R1 按每一行掩码处理目的地址，判断所得网络地址是否与该路由项相同（02:11–03:24）。H1 的掩码用于判断本地直达，R1 各条路由的掩码用于各自的匹配；不能把 H1 的掩码拿来代替 R1 整张路由表中的掩码。

若只有一条路由匹配，可按该行规定的下一跳或出接口转发；若多条都匹配，选择前缀最长、目标范围最具体的路由（03:24–04:38）。例如 `/22` 覆盖 1024 个地址，而其内部的 `/25` 只覆盖 128 个地址，后者能更精确指定目的范围。选择最长匹配有助于在上级聚合路由与下级具体路由同时存在时，把数据报交到更具体的方向。

课堂以目的地址 `206.0.71.130`，候选路由 `206.0.68.0/22` 与 `206.0.71.128/25` 演示（04:38–07:31）。`/22` 掩码为 `255.255.252.0`，第三字节 $71\,\&\,252=68$，得到 `206.0.68.0/22`，匹配；`/25` 掩码为 `255.255.255.128`，末字节 $130\,\&\,128=128$，得到 `206.0.71.128/25`，也匹配。比较 25 与 22，选择 `/25`。此结果与上一课学校四系的地址分配一致：学校的聚合块 `/22` 包含四系各自的具体地址块。

| 候选前缀 | 按位与结果 | 是否匹配 | 选择结果 |
| --- | --- | --- | --- |
| `206.0.68.0/22` | `206.0.68.0` | 匹配 | 作为候选 |
| `206.0.71.128/25` | `206.0.71.128` | 匹配 | 前缀较长，选中 |

补充反例：目的地址改为 `206.0.70.130`，与 `/22` 仍匹配；与 `206.0.71.128/25` 比较时第三字节 70 与 71 不同，因此只走 `/22`，前提是没有其他更具体路由。若还存在 `206.0.70.0/24`，则目的 `206.0.70.130` 会选 `/24`。解题时要对每条实际存在的路由各自计算，不能因为某个更长前缀看起来相近就直接采用。

## 用前缀树理解路由查询（07:31–11:17）

教师说明实际路由器面对大量前缀时，不会必须把每一个数据报与整个表从头到尾逐行比较；可以用按目的地址二进制位逐级组织的前缀树等数据结构提高查询效率（07:31–11:17）。课堂转写称为“二叉线索树”，这里按其描述的“每层检查地址的一位，0 和 1 分别走两个方向”理解为二进制前缀树。具体设备可能使用压缩前缀树、硬件 TCAM 或其他结构，不能认定所有路由器都采用同一种树。

构造思想：从根节点开始，第一位为 0 走一个分支，为 1 走另一个分支；继续按第二位、第三位逐层处理。某个路由前缀长 `/n`，就可在第 $n$ 位对应位置记录这条路由。查询目的地址时沿位序向下，保存沿途遇到的最后一个有效路由记录；若继续向下遇到更长且匹配的前缀，就更新候选。走到不能再延伸的位置时，最后保存的记录就是最长前缀匹配结果。IPv4 地址最多 32 bit，因此未压缩的逐位路径最长为 32 层。

补充例子：路由表有默认 `/0`、`10.0.0.0/8`、`10.4.0.0/16` 与 `10.4.3.0/24`。目的 `10.4.3.7` 沿位序下行，依次经过这些已记录前缀，最终取 `/24`；目的 `10.4.8.7` 只经过 `/0`、`/8`、`/16` 的有效记录，取 `/16`；目的 `11.4.3.7` 不匹配 `10/8`，取默认路由。树中可能存在只用于组织前缀、没有路由记录的节点，经过这种节点时仍保留上一条有效候选。

课堂练习要求判断若干地址是否与给定前缀匹配，并提示只需展开处在掩码边界上的关键字节，不必把全部 32 bit 都写成二进制（11:17–18:51）。例如 `/12` 已完整固定第一字节及第二字节的高 4 bit。比较两个 `/12` 地址时，只需确认第一字节相同，并检查第二字节的高 4 bit 是否一致。若第二字节为 35，其高 4 bit 为 2，对应范围 32–47；同一范围中的 40 与 35 在第二字节高 4 bit 相同，48 则进入下一范围。题目中的具体投影选项没有完整转写，不能把这里的数字当作原题答案。

**【理解重点】按位与计算用于判定某条路由是否匹配，最长前缀规则用于从多条匹配中选择。**这两个动作有先后关系。把“最长”理解成地址文本中数字最大，或把“匹配”理解成前几个十进制数字看起来相似，都会产生错误。

## ICMP 的差错报告与报文位置（18:51–22:51）

教师将 ICMP 作为 IPv4 网络层的控制报文协议介绍，主要用于主机或路由器报告某些网络层问题，以及开展诊断查询（18:51–20:37）。ICMP 报文封装在 IPv4 数据报中传送，首部包含 Type、Code 和校验和。Type 指定大的报文类别，Code 在同一类别内进一步指出具体情形；后续数据依 Type 与 Code 变化。因此“收到 ICMP”并不直接说明故障，Echo Reply 等信息也属于 ICMP。

课堂列举目的不可达、时间超出、参数问题、重定向等差错报告（20:22–20:56）。例如路由器转发时 TTL 下降到不可继续转发的状态，可向源端报告时间超出；出接口 MTU 过小且 DF 禁止分片时，可根据条件报告目的不可达中的分片需求信息。ICMP 差错报文通常携带原出错数据报首部及至少前 8 B 数据，让发送端识别是哪次通信触发了问题（20:56–21:38）。这些是诊断线索，不等于网络自动替原报文完成可靠重传。

ICMP 差错报告还有抑制条件：例如不对 ICMP 差错报文再次生成 ICMP 差错，也不因非首片分片、某些广播或多播目的、无效源地址等情形产生普通差错报告（21:41–22:25）。原因是防止一条异常信息引发成倍的额外控制报文，并避免把错误回复发给无法正确定位的源。课堂的概括便于理解，具体是否发送还受相应 ICMP 标准与设备安全策略约束。

补充判断：若主机向不存在的本地目的地址发送数据，可能先表现为 ARP 无应答，未必收到某个远端路由器的 ICMP；若路由器明确找不到下一跳，可能产生目的不可达；若防火墙过滤 ICMP，即使目标服务仍可用，发送端也可能看不到诊断回复。读网络测试结果时应区分“通信失败的原因”和“有没有收到差错报告”。

## `ping` 与路径探测的解释（22:51–25:50）

教师介绍 `ping` 使用 ICMP Echo Request 与 Echo Reply 检查对方是否按设置回复（22:51–23:39）。发送端记录是否收到应答和往返耗时，可判断这一类诊断报文的可达性与延时。若某台服务器禁用 Echo Reply 或网络中途过滤 ICMP，`ping` 没有应答不能单独证明服务器所有服务都不可访问；还需结合实际业务端口和路由情况判断。

路径探测程序通常利用逐步改变 Hop Limit 或 TTL，让沿途路由器在数值耗尽时返回时间超出信息，从而推断若干下一跳地址（23:41–24:21）。不同系统可能采用 ICMP Echo、UDP 探测或其他方式，最终目的端的反馈也可能不同。课堂口述把路径探测与“时间戳”放在一起；更准确的核心机制是让 TTL 或 Hop Limit 在逐跳发送中耗尽，再观察返回的 ICMP 时间超出消息。设备可能不回应、限制回应速率或隐藏地址，因此显示星号并不一定代表用户业务在该跳停止。

补充流程：对同一目的分别发送 TTL=1、TTL=2、TTL=3 的探测报文。TTL=1 抵达第一台路由器后不能继续转发，该设备可能返回时间超出；TTL=2 可到第二台设备，依此向外延伸。工具显示的是各次探测收到的回复地址与耗时，不保证这些回复恰好构成唯一且固定的一条真实业务路径，因为路由与负载分担可能改变每次探测的经过设备。

## IPv6 的基本设计与首部（25:50–33:20）

### 地址空间与固定首部

教师说明 IPv6 的主要推动因素是 IPv4 地址空间不足，IPv6 把地址长度从 32 bit 扩大到 128 bit；它仍采用无连接的数据报传送，并对首部处理、自动配置与扩展方式作出调整（25:50–27:28）。地址空间共有 $2^{128}$ 个不同的位串，远多于 IPv4 的 $2^{32}$。这不意味着所有 128 bit 位串都可直接分配给终端，也不意味着地址分配可以完全忽略层级、路由聚合和保留范围。

IPv6 基本首部固定为 40 B，后面是有效载荷；扩展首部若存在，排在基本首部之后，也计入有效载荷长度的计算范围（27:28–28:06；31:46–32:16）。与 IPv4 可变首部不同，IPv6 把附加功能通过一组扩展首部表达。常见基本首部字段包括 Version、Traffic Class、Flow Label、Payload Length、Next Header、Hop Limit、Source Address、Destination Address。读包时应按字段语义确定位置，不能把 IPv4 首部图按字节直接搬到 IPv6 上。

| IPv6 基本首部字段 | 长度 | 用途 |
| --- | ---: | --- |
| Version | 4 bit | 值为 6 |
| Traffic Class | 8 bit | 流量分类相关信息 |
| Flow Label | 20 bit | 标识相关报文流的线索 |
| Payload Length | 16 bit | 基本首部之后的负载字节数 |
| Next Header | 8 bit | 指明下一扩展首部或上层协议 |
| Hop Limit | 8 bit | 限制可经过的转发次数 |
| Source Address | 128 bit | 源 IPv6 地址 |
| Destination Address | 128 bit | 目的 IPv6 地址 |

Traffic Class 可配合分类处理，Flow Label 可为一组相关报文提供统一处理线索，但路由器是否执行相应服务策略取决于网络配置（29:54–31:38）。标出相同 Flow Label 不会自动形成虚电路，也不会由 IPv6 本身承诺固定带宽。`Payload Length` 计算的是基本首部之后的数据长度，包括存在的扩展首部；若没有特殊扩展机制，其 16 bit 字段可表示的普通值至多 65535 B，不能把该数直接当作包含 40 B 基本首部的整包总长度。

`Next Header` 类似 IPv4 的 Protocol 字段，但还可指向下一个 IPv6 扩展首部；每个扩展首部再提供自己的 Next Header，直到指向 TCP、UDP 或其他上层内容（29:02–29:39；32:17–32:47）。`Hop Limit` 与 IPv4 TTL 的逐跳限制用途相近，每经路由器减少，耗尽时丢弃（32:50–33:18）。IPv6 基本首部没有 IPv4 那样的首部校验和字段，数据完整性仍可能由链路层及上层协议负责。

补充计算：若 IPv6 报文基本首部 40 B，后面有 8 B 扩展首部与 1000 B 上层数据，则 Payload Length 为 1008 B，整个 IPv6 报文在这一计算中为 $40+1008=1048$ B。若题目要求判断下一协议，需沿 Next Header 顺序读过扩展首部，不能只看基本首部中的第一个 Next Header 值。

## IPv6 扩展首部与分片位置（33:20–38:01）

教师列举逐跳选项、路由、分片、鉴别、安全封装载荷及目的选项等扩展首部（33:20–34:13）。扩展首部按协议规定的顺序组织，相关处理位置也有差别；普通中间路由器通常关注转发所需字段，并非逐一执行所有仅面向终端的扩展功能。课堂对鉴别和安全封装载荷作概念介绍，真实安全属性由所选算法、密钥、模式和策略决定，不能只因存在某个扩展首部就断言具备全部机密性、完整性与不可否认性。

IPv6 路由器不在中途对过大的数据报进行分片；需要分片时由源端依据路径 MTU 及相关信息处理，目的端负责重组（34:15–35:24）。如果中间出接口 MTU 不足，路由器丢弃相应报文并报告 Packet Too Big，源端再调整后续发送大小。相比 IPv4 中路由器允许对 DF=0 的报文分片，这减少了中间转发节点的分片处理工作。课堂说“只允许你分一次”用于强调只由源端执行分片，不能理解为某次应用数据仅能产生一片。

扩展首部通过 Next Header 连接。例如基本首部的 Next Header 指向路由扩展首部，后者的 Next Header 再指向 TCP；接收方沿序解析，直到找到实际负载协议（36:40–38:01）。不同扩展首部的字段结构并不完全相同，不能把 Next Header 数值当成下一个字节的地址；它是标识后续首部类型的代码。课堂图示中给出数值 43 表示路由扩展首部，本节不要求默记每个数值。

## IPv6 地址类型与文本写法（38:01–49:59）

### 单播、多播、任播

教师按单播、多播和任播介绍 IPv6 地址用途（38:39–40:06）。单播用于指向一个接口；多播表示一个组，报文可送达组内相关成员；任播让一组接口共享一个任播地址，路由选择其中一个可达成员接收报文。任播可以用于把请求导向距离较近或路由上更合适的服务节点，但具体“最近”取决于路由策略及网络拓扑，不能保证它始终是地理位置最近或负载最低的设备。IPv6 没有 IPv4 的传统广播地址，组播承担许多面向一组设备的信息传递功能。

补充情境：某项 DNS 服务在不同地区部署多个节点，若这些节点正确配置相同任播服务地址，客户端发往该地址的一个请求由路由系统选择其中一处接收。若另一个节点更近但路由策略未把它作为首选，客户端仍可能到达其他节点。课堂以此类场景解释“交付给组中一个成员即可”，不能把域名查询中的多个不同 IP 地址直接等同于同一个任播 IP 地址。

### 冒号十六进制与零压缩

IPv6 的 128 bit 可写成八组 16 bit 十六进制数，用冒号分隔（40:06–42:16）。每组最多四个十六进制字符，组内前导零可以省略，例如 `0db8` 可写 `db8`。连续的全零组可用 `::` 缩写，但一个地址中只能使用一次 `::`，否则无法唯一确定两处各省略多少组（42:44–43:39）。没有使用 `::` 时，总共必须能还原为八组。

补充演算：`2001:0db8:0000:0000:0000:0000:0000:0001` 可以写为 `2001:db8::1`。展开时前面两组是 `2001`、`0db8`，最后一组是 `0001`，中间需要补足五组 `0000`。`2001:db8:0:1:0:0:0:1` 可压缩后一段连续三组零，写为 `2001:db8:0:1::1`；也可只省略其他一段符合规则的连续零，规范展示通常选择最长连续零段。`::` 表示一个或多个完整的零组；单组零也可以直接写 `0`。

课堂指出 IPv6 地址长度大、零较多，压缩有利于书写，但无论采用哪种有效缩写形式，展开后都要得到同一个 128 bit 位串（43:39–44:16）。做地址题时，先数显式组数，再补足八组；若看到两个 `::`，就判定文本写法有歧义。

### 典型范围

IPv6 环回地址为 `::1/128`，未指定地址为 `::/128`，常用于设备尚未取得正式地址等特定场景；前者表示本机，后者不能作为普通远端目的接口地址（44:23–46:36）。多播地址位于 `ff00::/8` 范围；链路本地单播地址位于 `fe80::/10`，用于同一链路的邻居发现等操作（44:44–45:45）。链路本地地址只在对应接口及链路范围内有意义，引用它时往往还需要指出接口。

教师还介绍全球单播与唯一本地地址 ULA（45:45–49:02）。全球单播地址面向全球路由管理；ULA 常用 `fc00::/7` 范围，其中实际常见本地生成形式位于 `fd00::/8`，为组织内部的地址规划提供空间。ULA 具有较低的随机碰撞概率，不等于可以不经路由与安全配置就直接在全球互联网公开传送。课堂把历史站点本地地址与后来 ULA 的概念连在一起；学习时按各自用途区分，旧站点本地地址范围已不作为当前通用的新分配方式。

全球单播地址可以按组织分配方案划出全球路由前缀、子网标识和接口标识；教师用 48 bit、16 bit、64 bit 的组合说明一个常见 `/48` 机构前缀下可分配 `/64` 子网的结构（49:04–50:21）。这是一种典型规划，不能作为所有全球单播地址的强制固定比例。若取得 `/48`，剩余 16 bit 可表示 $2^{16}$ 个不同 `/64` 子网编号；每个 `/64` 中仍有 64 bit 接口标识空间。数量多也需要按路由和管理边界规划。

补充地址练习：`2001:db8:12:34::5/64` 展开为 `2001:0db8:0012:0034:0000:0000:0000:0005/64`。前 64 bit 正好是前四组，因此所在 `/64` 子网前缀可写 `2001:db8:12:34::/64`，后四组是这一地址中的接口标识部分。若机构取得的是 `2001:db8:12::/48`，前缀只固定前三组，第四组 `0034` 属于该机构可选择的 16 bit 子网编号。读到 `/48` 与 `/64` 时，应先按 16 bit 一组定位边界，再判断哪一组表示子网编号、哪几组属于接口标识。

若地址写成 `2001:db8::5`，八组展开过程必须明确：第一组为 `2001`、第二组为 `0db8`、最后一组为 `0005`，中间省略五组全零。若地址是 `2001:db8:0:0:1:0:0:5`，存在两段相同长度的连续零组，可以选择其中一段进行 `::` 缩写，但不能同时缩写两段。若只数冒号数量，容易把两端的零组数计算错误；按显式组数补足八组更可靠。地址文本表达的灵活性不会改变它的 128 bit 实际数值，也不会改变前缀长度的含义。

判断 IPv6 地址能否在某条链路上直接使用，还要看地址类型与作用范围。`::1` 应由本机处理；`fe80::/10` 的链路本地地址通常只用于所在链路，跨路由器不能直接沿用同一作用范围；全球单播地址则需要相应的路由可达性。一个接口可同时拥有链路本地地址和全球单播地址，二者适合不同用途。设备进行邻居发现时会使用 IPv6 本身的邻居发现机制，不能把 IPv4 的 ARP 报文原样用于 IPv6。

## IPv4 与 IPv6 共存方式（50:21–51:05）

教师在课末提到双协议支持和隧道技术两条过渡路线，并开始说明双协议设备能分别处理 IPv4 与 IPv6 流量（50:21–51:05）。双协议设备同时具备两种协议能力，但这不意味着收到一个 IPv6 数据报后可以无条件逐字段转换为功能完全相同的 IPv4 数据报；两种首部字段、地址长度和服务能力存在差异。若确需跨协议通信，还要采用适合的转换或代理机制。隧道则可把一种协议的数据报封装进另一种协议的数据报，穿过中间只支持外层协议的网络；本节仅提出名称，具体封装在后续课次再核实。
